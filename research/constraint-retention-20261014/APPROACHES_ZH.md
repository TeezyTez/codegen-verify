# 现有方案与工程建议

## 方案比较

所列官方实践可以归纳为五类。它们针对不同失效环节，通常需要组合使用；产品提供某种能力，并不构成该能力普遍有效或优于其他方案的实验结论。

| 方案 | 核心做法 | 主要解决的问题 | 保证边界 |
| --- | --- | --- | --- |
| 持久化规则 | 把稳定约束写入项目文件，按范围加入上下文 | 跨轮、跨会话缺少项目约定 | 加载规则不保证理解或执行正确 |
| 规格驱动与任务清单 | 将需求写成规格、计划、任务和验收条件 | 附加要求被漏掉、任务过早结束 | 规格抽取本身可能遗漏或曲解需求 |
| 上下文管理与外部记忆 | 检索、压缩、结构化进度与显式交接 | 上下文过长、恢复任务时缺少状态 | 检索可能漏召回，摘要可能丢失限定条件 |
| 自动检查与门禁 | 测试、静态检查、权限、工具前检查和 CI | 约束可见但执行违规 | 只能覆盖已编码且可判定的条件 |
| 按需求验收与独立审查 | 逐项关联原始需求、实现和验证证据 | 自报完成、缺少全局核对 | 审查者也可能遗漏，主观要求仍需判断 |

## 持久化规则

Codex 使用 `AGENTS.md` 提供项目指导；Cursor 提供始终加载、按文件匹配、由代理选择和手动引用等规则方式；GitHub Copilot 支持仓库级与路径级指令。具体加载范围应以相应工具文档为准。[Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Cursor](https://cursor.com/docs/rules)、[GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)

Claude Code 区分用户维护的指令文件和代理积累的自动记忆，并明确将二者视为上下文，而非强制配置。[Claude Code 记忆文档](https://code.claude.com/docs/en/memory)

工程上宜将长期稳定约束放在简短项目规则中，将当前功能的要求放在任务规格中。定期清理失效和冲突内容；规则增加后，应检查它们是否进入实际工作上下文。

## 规格驱动与需求追踪

GitHub Spec Kit 将自然语言需求推进为规格、计划和任务，并提供一致性与完成度检查流程。该流程将需求保存成可重复读取的工件，方便实现前后核对。[Spec Kit 指南](https://github.github.io/spec-kit/quickstart.html)

建议给需求编号，明确行为、范围和验收条件，并保留到原始需求的对应关系。新增或变更需求时，更新有效版本，避免旧任务清单继续驱动实现。

| 需求示例 | 可以核对的条件 |
| --- | --- |
| 保持向后兼容 | 旧参数仍可接受，约定返回字段仍存在，旧调用方式通过契约测试 |
| 不新增依赖 | 按约定范围比较依赖清单与锁文件 |
| 指定目录不可修改 | 检查版本差异；必要时配置写入权限 |

测试应依据需求设计。只根据已实现的代码补测试，可能把实现中遗漏的要求一起遗漏。

## 上下文管理与任务交接

Anthropic 的上下文工程实践讨论了即时检索、压缩、结构化笔记和子代理隔离。其长任务案例使用功能清单、进度文件与版本历史，帮助后续会话恢复任务状态。[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[长任务案例](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

建议把少量关键约束固定加入工作上下文，把大量背景资料按需检索；不让关键约束仅依赖语义相似度召回。交接内容至少覆盖当前目标、有效约束、未完成事项、相关文件与已获得的验证证据。子任务接收的约束需要明确传递。

扩大上下文窗口、增加 RAG 或增加代理数量都不能单独保证遵循。更多上下文仍可能包含无关或冲突信息；检索有召回边界；多代理增加了交接与结果整合的要求。

## 自动检查与执行门禁

Claude Code 的命令型 hooks 在指定生命周期事件运行程序，可用于执行检查或阻止操作。使用模型判断的 prompt 或 agent hooks，仍包含模型判断的不确定性，不能与确定性程序检查混为一谈。[Hooks 文档](https://code.claude.com/docs/en/hooks-guide)

按约束性质选择检查位置：工具调用前检查可以阻止某些操作；修改后的差异和测试可以发现结果偏差；必需的 CI 检查可以阻止不满足条件的合并。保障强度取决于检查覆盖范围、权限和是否存在未受检查的操作路径。

自动检查适合明确的依赖策略、接口契约、文件范围与类型约束。代码是否易理解、交互是否自然等要求通常需要人工或模型审查。任何“通过”结论都应限定到实际检查的条件。

## 验收与完成证据

Anthropic 的长任务案例将功能是否通过与验证联系起来，处理代理提前宣布完成以及缺少端到端验证的问题。案例展示了一种工程方案，不能直接推广为所有任务上的效果保证。[长任务案例](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

建议验收记录包含需求编号、实现位置、检查方法与结果。没有运行验证的要求应标记为未验证；单纯勾选任务或代理自报成功不能替代证据。若引入独立审查，审查者需要读取原始需求及有效变更，避免只依赖实现者的总结。

## 最小工程组合

1. 一份简短项目规则，保存长期约束及任务规格入口。
2. 一份当前任务规格，保存需求编号、验收条件和变更记录。
3. 对关键可判定约束配置自动检查，并在合适位置执行。
4. 完成前逐项核对原始需求、代码差异与验证证据。

复杂任务再增加检索、结构化交接、独立审查与运行日志。文件名和工具可以不同，关键在于约束能被恢复，结果能被核对，原因能被追踪。

## 待验证的研究问题

以下问题由本次机制分析提出，尚未进行受控实验或新颖性核验：

- 在相同任务、模型和预算下，约束固定加载、按需检索与交接时重申，对违规率分别有什么影响？
- 上下文压缩和任务交接是否更容易丢失适用范围、否定条件或例外？如何与约束已传入但执行失败的情况区分？
- 在已有规则与测试的基础上，需求编号、证据对应和独立审查能否减少漏项及过早完成？增加的成本是多少？
- 自动门禁能够发现或阻止多少违规，又会产生多少误报、额外修复和延迟？

候选指标包括需求覆盖率、违规率、发现率、阻断率、误报率，以及 token、时间和工具调用成本。对照需要控制任务难度、模型和预算；违规归因需要可观察的上下文或交接记录，无法观察时不能强行归类。它们与仓库既有的固定规约验证结果应分别报告。

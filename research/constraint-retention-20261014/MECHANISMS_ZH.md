# 约束保持机制与失效分类

## 一条约束如何延续

以“本任务全程不得新增第三方依赖”为例，后续开发需要持续获得该约束、理解其适用范围，并在修改代码和验证结果时落实它。普通对话中的指令通过上下文影响生成，不会因为提出过一次，就成为模型参数中的永久规则。

可以按四个环节分析：

```text
约束进入当前上下文 → 正确理解适用范围 → 在代码和工具操作中执行 → 检查结果
```

应用通过历史消息或会话状态维持多轮交互。OpenAI 的会话状态文档说明了传入先前消息、链接响应等方式。用户界面中保存的完整历史，与一次调用实际获得的上下文，不应直接视为同一份内容。[会话状态文档](https://developers.openai.com/api/docs/guides/conversation-state)

对话、代码与工具输出变长后，系统可以压缩上下文，使用较少的内容携带后续需要的信息。压缩的具体形式因实现而异；OpenAI 文档所述压缩项可以是不可直接解读的状态，不能统一称为可读文字摘要。压缩旨在维持连续性，但不应由此推断每个细节都会原样保留。[上下文压缩文档](https://developers.openai.com/api/docs/guides/compaction)

项目规则提供另一条恢复路径。例如 Codex 在启动时按规则发现并组合 `AGENTS.md`，发现过程受目录、覆盖顺序与大小限制影响。文件持久存在，能够帮助后续任务重新获得规则，但不能单凭文件存在判定某次调用已加载它。[AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 失效分类

下表是诊断分类，不是对任一产品故障频率或具体会话内部状态的测量。

| 环节或事件 | 可能的失效 | 需要区分的情况 |
| --- | --- | --- |
| 历史传递 | 新任务、历史裁剪或上下文选择没有带入约束 | 历史仍存储在界面或磁盘，不代表当前调用可见 |
| 上下文压缩 | 约束、限定词、例外条件或未完成事项没有充分保留 | 一次违规不足以证明由压缩造成 |
| 规则加载 | 目录范围、覆盖规则、配置或长度限制导致未加载 | 文件存在、被加载、被执行是不同状态 |
| 子任务交接 | 子代理或接手任务只得到局部目标，缺少相关约束 | 上下文继承取决于工具和传递方式，不能一概认为共享全部历史 |
| 理解 | 把整个项目的约束理解成当前模块或当前阶段的约束 | 原文可见仍可能发生范围判断错误 |
| 执行 | 处理局部问题时，没有把已理解的约束落实到修改或工具调用 | 能正确复述约束不等于实现满足约束 |
| 验证 | 没有对应检查，或测试与实现遗漏了同一个要求 | 测试通过只支持已覆盖的条件 |
| 规则更新与冲突 | 后续要求改变适用规则，或模型误判发生了改变 | 用户明确更新规则不属于遗忘；把局部例外误当全面放宽属于错误 |

指令优先级也会影响约束的适用性。旧约束被合法更新，或在冲突中不再适用，与记忆丢失应分别记录。

## 如何诊断一次违规

先确认当时有效的需求版本和作用范围，再检查可获得的调用上下文、规则加载记录、交接内容与代码差异。若没有这些证据，应将原因保留为未确定，而不是直接归因于上下文长度或压缩。

建议记录以下信息：

- 约束原文、来源、作用范围与明确的变更记录。
- 该次调用或任务实际获得的相关规则；无法观察时明确标记未知。
- 产生违规的修改或工具操作，以及验证结果。
- 独立审查发现的问题和修复后重新验证的证据。

让模型复述当前约束可以作为辅助检查，但自述不能代替实际输入记录与代码证据。外部观察通常能够定位传递缺项或结果违规，不能直接证明模型内部如何理解一条指令。

## 更明确的约束表达

以下是工程示例，适用于需要严格限制依赖变更的任务：

> 本任务全程不得新增第三方依赖，适用于功能实现、重构、测试修复和子代理任务。只有用户明确修改此规则时才可放宽。完成后检查依赖清单与锁文件，确认没有新增依赖。

实际项目还应按需要定义“新增依赖”是否包括开发依赖、间接依赖和工具安装。避免将不明确的范围留给执行阶段猜测。

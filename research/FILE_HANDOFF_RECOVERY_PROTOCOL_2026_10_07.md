# 跨午夜交接故障后的恢复检查

保存于新模型采样前。原 `file-repair-development-20261006` 的 96 次开发矩阵已因输入审计异常永久停止：8 次有效通过、3 次协议中止、85 次未启动。两份未接收的回答不追认，也不作为算法失败。冻结源码快照、原审计和中断用量单独保留。

## 原因及修复

平台跨午夜自动发出第二条 `environment_context`。原逻辑只允许一条 user 消息，因而误报额外任务。协议升级为 `verified_file_repair_exploratory_v2`：必须从原会话日志核验平台 metadata 类型、严格解析环境字段；只允许日期同日或向前一天，其他出现的字段必须与初始环境一致。禁止普通用户追加、第二个 agent 任务、额外文本、未知字段和环境权限变化。实际加载命令、完整 stdout、工具次数、唯一最终答案、来源和模型身份继续审计。新规则不追溯改变 v1 样本资格。

## 固定恢复检查

本阶段仅检查修复后的完整采集—修复—验证链路，不是新的 96 次矩阵，也不作为方法有效性证据。

- 使用触发故障时正在运行的 `prefix_maxima`，A/B/C/D 各 1 次，共 4 次新运行。
- 组顺序用种子 20261007 在运行前冻结；2 个并行任务，避免三个排队任务争夺两个可用 solver 槽。
- 不调整题目、失败起点、策略、系统修复指令、Dafny 版本和原每次运行预算：最多 3 次 solver 请求、4 次全文件验证；15 秒验证、600 秒请求、2400 秒运行。
- 共最多 12 次 solver 请求、16 次题内验证；参考与起点另做 2 次准入验证。模型 gpt-6-astra/high。费用未知，无硬 token 上限。
- 每次请求全新上下文、固定单次加载器；没有父会话历史、参考代码和其他组结果。平台上下文仍存在，此方案不是 OS 沙箱。
- 四次按计划结束，不因成功率临时加题/加重复。算法失败照常计数、预算内继续；身份、源码、交接错误按预设立即停止。
- 恢复判据是 4 次运行全部终止且交接与工件审计通过，不要求模型全部答对。额外使用真实跨午夜日志只读回放环境审计；该回放不计为新模型样本。

恢复检查报告后，再启动独立冻结的完整开发矩阵。此阶段与 v1 及其他旧协议不混合汇总。原 96 次计划仍未完成，不能用这 4 次替代。
